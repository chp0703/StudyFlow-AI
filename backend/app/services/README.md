# A2 task service — integration draft

`TaskService` implements candidate creation, internal edit, confirmation and owner-scoped search. `task_handlers(service)` supplies the three public dispatcher handlers. Inject the store, a timezone-aware clock and UUID factory; `TrustedContext` must be built by authenticated server code, never from LLM arguments. No auth provider, database or TV3 state machine is implemented here.

## PROPOSED transaction/evidence seam — TV1 and TV3 review required

`store.transaction(owner)` returns a context manager; all methods below execute against the same owner-protected transaction and authoritative snapshot. The real implementation must provide rollback, isolation, conditional versions, same-owner constraints, unique task per candidate and atomic replay records. The test fake does not demonstrate those database guarantees.

* `get_message(message_id)`: authenticated server-side message `{message_id,user_id,conversation_id}`.
* `get_candidate(id)`, `save_candidate(candidate)`, `find_task_by_candidate(id)`, `save_task(task)`, `search_tasks(owner,query,statuses,page_size,cursor)` and `increment_schedule_revision(owner)`. Search returns `(items,next_cursor)`; cursor ordering/encoding and upper page-size limit are transport/TV1 decisions. The service validates schema, length and owner of returned items.
* `get_pending(action_id)`, `get_review(action_id,action_version)`, `complete_pending(action_id,action_version)`: pending includes owner, conversation, version, state, candidate and `requires_review`; review is an immutable server-side record of the displayed target/version and full normalized slots, including default priority. Completion must conditionally update the same version atomically; TV3 owns the conversation state machine.
* `get_decision(approval_action_id)` returns the server-retained UserDecision, owner, conversation, source (`CHAT` or `UI`) and source message/event reference. `get_decision_source(approval_action_id)` returns an **independently authenticated backend source record** binding the same owner, conversation, source, message/event and exact decision. It must not be a second copy of arbitrary LLM/client data or a boolean assertion. For CHAT, `get_message` verifies the referenced message; for UI, `get_ui_event(event_id)` verifies the authenticated event and its exact decision. The mapping from a verified action to this internal ID and record lifecycle is unapproved and needs TV3/auth review.
* `save_approval(record)` persists the verified schema-v1.1 ApprovalAction within the same transaction. It is not proof of authorization by itself.
* `get_idempotency(owner,operation,key)` and `put_idempotency(owner,operation,key,fingerprint,result)` handle the official `create_task_candidate` and `confirm_task` operations. Returned records include `{fingerprint,state,result}`. Under the owner lock, the same completed fingerprint replays before stale checks; different fingerprints conflict. An `IN_PROGRESS` or malformed record fails closed with `INTERNAL_ERROR`; its recovery/retry policy is not yet agreed. The TV1 backend must atomically complete this with business writes.
* Internal edit uses `get_internal_edit_replay(owner,key)` and `put_internal_edit_replay(owner,key,fingerprint,result)`, with the same transactional behavior, in a **separate private namespace**. `edit_task_candidate` is not a public operation and must not be written as `IdempotencyRecord.operation` unless the shared schema is formally changed. The persistence strategy and retention for this private mechanism need TV1 review.

The A2 service checks the current candidate and displayed content again, compares JSON types without treating booleans as integers, validates date-only cutoff against the named timezone, and does not reject a task just because its deadline is past. Draft edit increments candidate version; older decisions no longer match. It normalizes `priority=NORMAL` before display, so the review must bind that value. No relative-date interpretation is performed. Timestamp validation retains the dispatcher's documented limitation for leap seconds/year 0000; local date cutoff rejects nonexistent or ambiguous midnight.

Use `python -B -m unittest discover -s tests -v` with `jsonschema` available. The `MemoryStore` in tests is a fake, including fake verified sources; its IDs, pagination and in-memory rollback are test data only. Until TV1/TV3/auth review and real integration, do not treat this as evidence that stored decisions, authorization, durable rollback or concurrent requests are secure.

## A3 and A6 — proposed seams, not shared approved interfaces

`SettingsService(store, validate_window=..., warnings=...)` implements the three A3 operations; `settings_handlers(service)` adapts them to Dispatcher. It reuses A2's decision/source checks, the existing command/result schemas and `merge_scheduling_policy`. The review evidence must bind `PENDING_ACTION` to the current action/version and `displayed_action = {operation, arguments, effective_policy}`; for windows `effective_policy` is null, for preferences it is the **entire merged policy**. The pending action's `draft_arguments` must match the command. This presentation shape is internal and proposed to TV3, not a new public DTO.

The owner-scoped TV1 transaction additionally proposes `get_profile(owner)` returning user_id, full scheduling_policy and schedule_revision; `get_window(id)`; `save_window(window)`; `save_policy(owner,policy)`; and the existing conditional `complete_pending`, `increment_schedule_revision`, approval and idempotency methods. All must share one owner-protected atomic transaction. Results and warnings replay together before stale checks. Failed writes must roll back approval, pending action, revision, data and receipt; only the in-memory fake has been tested here. Record storage, locking and replay concurrency require TV1 review and real-DB tests.

`validate_window(window)` is a required TV4 pure callback returning a list of issues; any issue blocks the write. It must check all temporal/recurrence/timezone semantics that JSON Schema cannot establish. `warnings(snapshot, change)` is a separate required pure callback; `snapshot = tx.get_warning_context(owner)` is a proposed same-owner snapshot assembled by TV1/TV2. It reports whether the prospective change affects the current plan; fake callbacks in tests are not a real validator and do not establish scheduling safety. Neither callback receives a transaction or writes to it. The service does not change current plan or task remaining minutes.

`PlanReadService(store, warnings=...)` implements CURRENT/HISTORY/PROPOSAL; `plan_read_handler(service)` adapts it to Dispatcher. Proposed TV1 read methods are `get_current_plan(owner) -> (plan|null, blocks)`, `get_plan_by_version(owner,version) -> (plan|null, blocks)`, `get_proposal(owner,id) -> proposal|null`, and the same `get_warning_context(owner)` for a pure current-plan warning callback. The store must provide a consistent same-owner snapshot, and blocks must belong to the returned plan and owner. Filtering uses half-open overlap and operates on copies only. Per schema v1.1, the proposal view can be filtered without changing the stored snapshot; contract package 1.0.0 instead proposes rejecting a PROPOSAL time filter. This conflict requires consumer review and is not silently adopted.

The separate shared contract package 1.0.0 is REVIEW_READY, not approved. Compared with its checker (date-time checker explicitly enabled), all 10 current valid command fixtures pass; the existing generated/rejected proposal fixtures fail its semantic coverage/diff checks, and the provisional generation READ fixture has a different shape. The newer proposed `SchedulingReadData` uses `kind`, `coverage`, `task_summaries`, and `plan_diff`; the existing provisional fixture uses `current_plan`, `conflicts` and `warnings`. No public READ shape or IC-01..08 decision is approved by this code. OpenAPI and real authentication/DB/TV4 integrations were not validated here.
