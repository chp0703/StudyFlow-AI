## Secure boundary and infrastructure

- Create sf_rpc_owner NOLOGIN NOSUPERUSER NOBYPASSRLS; do not grant membership to user roles. Every app_api wrapper is SECURITY DEFINER owned by this role, search_path empty, fully-qualified objects and minimum touched-table privileges. ENABLE/FORCE RLS for all private tables; owner policies derive auth.uid(). Global contract/key tables have role-specific read policies. Revoke all authenticated/anon/PUBLIC private schema, table, sequence, helper privileges and default PUBLIC function EXECUTE. Remove old exposed overloads and issue_chat_approval_attestation bypass.
- Create infrastructure tables exactly mapped by data-contract: conversation_records, source_messages, api_request_receipts, action_presentations, rpc_attestation_keys; support owner/target/version/FK/immutability constraints. Align typed approval FK column names with data-contract. Preserve historical data and logical business fields.
- Implement app_private.canonical_json(jsonb) -> text with Unicode code-point sorting, UTF-8, JSON escaping, compact arrays/objects, bool/null and safe integers only. Reject fractional/decimal numeric lexical forms and out-of-range integers with SQLSTATE 22023. Do not hash jsonb::text as if canonical.
- Implement app_private.verify_rpc_request(jsonb, text) -> uuid. Require verified auth.uid(), principal/owner binding and matching routine. Mutations require HMAC-SHA256, active key, exact payload schema, duplicate JSON key rejection before jsonb coercion of the base64url payload, matching normalized-envelope digest, exact 60-second lifetime and <=5 seconds future skew; compare signatures without a content-dependent early exit. Reads require null attestation. Security failures raise 42501/FORBIDDEN or 28000/UNAUTHENTICATED inside this private helper. Public wrappers catch and return the declared ErrorResult without leaking SQL details.
- Bootstrap a profile safely/idempotently from the trusted owner (defaults Asia/Ho_Chi_Minh, vi, and full default scheduling policy). No service_role credential in normal user requests. All mutation wrappers require attestation including bootstrap/message/action/receipt paths.
- Add contract-backed JSON shape checking. Supabase ships pg_jsonschema (extensions.jsonb_matches_schema(schema json, instance jsonb)); use it with an embedded generated copy of the approved $defs and reject unsupported/unknown fields. A deterministic bundling script may produce a migration from contracts/schemas/f1.schema.json; Sol runs the generator. Do not silently regenerate manually changed schemas or alter the approved contract. Keep semantic/version/ownership checks explicit; extension shape validation is not authorization. Reference https://supabase.com/docs/guides/database/extensions/pg_jsonschema .

## Atomic writes and state

- All owner writers follow one row-lock protocol on user_profiles; domain mutations use fast domain lookup then lock then lookup again. Approval-bearing business mutations write their business data, ApprovalAction, action completion and domain idempotency in the same RPC. Draft/message/review/receipt operations do not manufacture ApprovalAction records; transport receipt keys never occupy the domain operation namespace. Technical failures rollback inside the wrapper exception subtransaction. When approval invalidates a stored proposal because its authoritative base/revision is stale, persist STALE and the terminal replay result without raising away that state (acceptance DB-06); a technical failure must not leave such partial business changes.
- Fingerprint exactly the stable normalized business request/decision binding from approved section 7, never request_id/time/new message ID/generated proposal IDs. Generation namespace is generate_study_plan and fingerprints original command_arguments. Idempotency and transport receipts retain at least 7 days. Old key/different payload conflicts; same key/completed response replays before stale checks and refreshes response request_id.
- Source messages must belong to a durable conversation/owner and use server IDs; receipt recovery preserves message/action IDs. Presentations bind full normalized content, target/version, effective merged policy and PARTIAL visibility. One awaiting action per conversation. Review/cancel/edit have conditional versions; candidate edits invalidate prior presentation. Reject candidate/window/policy cancels without business write; reject proposal preserves current plan/revision.
- claim/renew/release/complete receipts implement 120-second leases, lease_version fencing and terminal/transient distinction per contract; no product TTL for drafts/pending/proposals. Support deterministic workflow recovery rather than in-memory-only state. Demonstrate that a reclaimed lease rejects the old worker's renew/release/complete, preserves stable message/action IDs and replays durable completion after reconnect. A busy/retryable 429/503 result must not become a terminal receipt. Do not invent a lease-specific error enum absent from the contract.

## Core domain and planning

- Implement signed source->candidate->confirm->search with exact types/results, source/presentation/approval binding, DATE deadline semantics, one task per candidate/backlink, and schedule revision increments only for scheduling-affecting writes. Never trust a p_decision boolean alone or fabricated CHAT provenance.
- Implement TimeWindow ADD/UPDATE/ARCHIVE, full policy merge/revision guarding, current/history/proposal reads and pagination per approved defaults. Expose no manual block or official task update/delete APIs.
- get_scheduling_context uses one SQL snapshot including full current plan and consistent revision. persist_plan_proposal accepts the complete canonical proposal and original command, validates scope/effective policy/revision and persists only FULL/PARTIAL with actual diff and no hard conflict.
- Approval reloads authoritative data under owner lock; checks exact base plan/version/revision, current now, pending/presentation/decision/partial visibility, ownership, full snapshot, workload, availability/busy/recurrence and effective policy. Read payload.study_blocks, not blocks. Only newly generated/moved blocks must not start before now; protected history remains immutable. Shared TV4 Python validation runs in TV2 too, but does not remove DB commit checks.
- Same-owner FK and backlink constraints, retained/protected ID continuity, snapshot immutability, per-plan [start,end) overlap, atomic plan+all blocks+pointer+revision+proposal+approval+action+replay commit are mandatory. Test history against actual UPDATE/DELETE attempts with ordinary RPC-owner privileges, not only catalog flags. Two competing proposals for the same owner/base must serialize even when their actions belong to different conversations. No LLM/network/Python execution inside SQL transactions.
